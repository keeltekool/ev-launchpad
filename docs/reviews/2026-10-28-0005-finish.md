### R1 [Critical] The live Launchpad passcode is committed and pushed in a unit test
- Where: `src/lib/board.test.mts:156-162` (added in `79ec663`, already on `origin/master`, `keeltekool/ev-launchpad`)
- Failure: The test sets `LAUNCHPAD_PASSCODE = "T\u00fcranahk"`. The passcode in `.env.local` contains the same word; I checked by match count without printing it. The commit says "owner's new passcode has ü". Anyone who can read the repo can open `/?key=…` and see every app's error titles. They can also make the cookie offline, because it is just sha256 of `launchpad:` plus the passcode (`src/lib/passcode.ts:10`). This breaks the §0 rule that secrets never go in code.
- Fix: Change `LAUNCHPAD_PASSCODE` in Vercel (production and preview) and in `.env.local`, then redeploy. The test should use a made-up value such as `"Gr\u00fcn-test"`. Deleting the line is not enough: it stays in git history, so the passcode itself has to change.
- Confidence: CONFIRMED

### R2 [Important] One "last heard" query failing marks healthy full-SDK apps as "Silent"
- Where: `src/lib/sentry.ts:81`, `:93-94` (introduced by `1bd03fa`)
- Failure: Say the spans query fails (400, 401 or timeout) and the errors query succeeds. `heardRows` is then not null, so an app with `firstTransactionEvent: true` and no errors in 14 days gets `lastHeard = null` and `silent = true`. Every such app then says "Silent… Is its Sentry wiring broken?" Before this commit, a failure hid the line instead. The unit test only covers the case where both queries are refused (`board.test.mts:194-196`).
- Fix: Keep spans success and errors success apart. Only calculate `silent` when the spans query answered, and leave `lastHeard` undefined if either query failed.
- Confidence: CONFIRMED

### R3 [Important] One bad "last heard" row takes down all Sentry data
- Where: `src/lib/sentry.ts:84-87`
- Failure: If a row's `max(timestamp)` is missing, null or a numeric string, `new Date(...)` is invalid and `.toISOString()` throws a RangeError. That happens inside the outer `try`, so the whole summary returns `{ ok: false }`. The board then says "Sentry unreachable" and drops every new-error problem, all because of a query the code treats as optional. The spans dataset's response shape has changed before (plan Task 1.3 deviation). This is the same kind of bug `1bd03fa` fixed in `checkJobs`.
- Fix: Skip rows whose parsed date is `NaN` before calling `toISOString()`.
- Confidence: PLAUSIBLE

### R4 [Important] Nothing limits passcode guesses, and the reason given for that no longer holds
- Where: `src/app/api/unlock/route.ts:9`, `src/proxy.ts:14`
- Failure: Both `POST /api/unlock` and `?key=` accept guesses without limit. The Gate 2 answer (`docs/reviews/2026-10-23-phase2-gate.md:49`) relied on "the passcode is 15 characters". The passcode changed on 24.10 to what the test shows: a single 8-letter word. Online guessing against a short word is realistic.
- Fix: Since the app has no storage for a rate limit, make the rotated passcode from R1 a long random string (20+ characters). Optionally, add a fixed delay of about 500 ms on a wrong guess.
- Confidence: PLAUSIBLE

### R5 [Minor] The last-ran check still accepts a non-numeric window and treats a future `lastRan` as on time
- Where: `src/lib/health.ts:136`, `src/lib/board.ts:175`
- Failure: `j.lateAfterHours > 0` passes for `true`, `"30"` and `[5]`. With `true`, the job is late after 1 hour, a false red. A `lastRan` in the future, from a clock or timezone bug in the app, gives a negative age, so the job never shows as late.
- Fix: Require `typeof j.lateAfterHours === "number" && Number.isFinite(...)`, and reject a `lastRan` more than a few minutes ahead of now.
- Confidence: CONFIRMED

### R6 [Minor] Job names from other apps go into the copied prompt unfenced
- Where: `src/lib/prompt.ts:233`, `:241`
- Failure: `j.job` comes from another app's public `/api/last-ran` reply and is pasted raw into the Claude Code prompt. Newlines and instructions survive, unlike the Sentry text, which goes through `data()` and the fence.
- Fix: Use `data(j.job)` in `lateLines`.
- Confidence: CONFIRMED

### R7 [Minor] The area shown for an issue is its oldest one, not its newest
- Where: `src/lib/sentry.ts:89`
- Failure: Rows are sorted newest first, but `new Map(entries)` keeps the last duplicate. An issue with several `area` values (possible in ApplyKit, which uses the full SDK) shows the oldest.
- Fix: Set a key only if it is not already in the map.
- Confidence: CONFIRMED

### R8 [Minor] "Came back in the last 24 h" is measured by last seen, not by when it came back

## Checked and sound
- **Access:** `proxy.ts` covers every route, including RSC requests, and only `/unlock` and `/api/unlock` are exempt. It fails closed when the env var is unset, compares in constant time, and sets an httpOnly, Secure, SameSite=Lax cookie. Launchpad's own health check follows the redirect to `/unlock` without recursing into the board.
- **Secrets:** the Sentry token stays on the server. Client files import only types from `sentry.ts`, `board.ts` and `apps.ts`. `SENTRY_API` and `LAUNCHPAD_EXTRA_APPS` are ignored in production. `.env*` is gitignored.
- **Health check:** redirects are followed by hand (5 hops), and one 10 s signal covers the whole chain. A timeout and a refused connection read differently. 401/403 count as up. Fluid compute is confirmed on, so a hung app can't time the function out (gate review evidence).
- **Board logic:** ordering, the uptime/watched split, slug matching by app name, the honest headline when Sentry is down, the problem prompt combining down, error and late, and the fence on Sentry text (unit-tested against a fence-escape attempt).
- **Reporter:** `report()` sends only from Vercel production, at most once a minute per failure kind; stack frames are parsed with node internals marked as not app code.
- **UI (§4):** solid `:focus-visible` outline in brand ink, no shadows in `globals.css`, a single solid primary action, and a flow check for no sideways scroll at 375.
